## 补充日志：MCP 心跳告警与数据库连接错误

日志覆盖北京时间 10:01:00.423–15:09:52.052；截图中的 15:52 不在该归档文件范围内。37,266 行日志中有 36,660 条带时间戳记录，其中 36,475 条来自 `KeepAliveScheduler`，占约 99.5%。按完整 UUID 去重，`Stream unavailable` 涉及 67 个会话；同一会话最多重复 1079 次，持续约 4.5 小时，峰值每分钟 265 条心跳告警。

当前配置显式启用每 15 秒一次的服务端 ping。核对现场同版本 SDK 0.18.3 的源码，调度器遍历所有注册会话；`McpStreamableServerSession.sendRequest()` 向独立的监听流发送请求，没有 GET 监听流就会报不可用。发送失败只记 WARN 并继续下一轮，既不停止该会话的探测，也不移除会话。仅通过 POST 调用工具的正常客户端也可能没有这个监听流，所以不能把所有告警都解释为数据库断连或无效会话。上游问题见 [Java SDK #1022](https://github.com/modelcontextprotocol/java-sdk/issues/1022)。

修复去掉默认 `keep-alive-interval: 15s`，使用 SDK 的默认关闭状态，停止主动向所有会话周期性发送 ping；POST 初始化和后续工具调用继续有效。外部部署若另外配置了该项，也需删除覆盖值并重启。不要改成 `0s`，该 SDK 以 null 判断是否创建调度器。没有调整日志级别，也没有依据一次 ping 失败删除正常的 POST 会话。

该修改止住重复 ping 带来的日志和调度开销，不等于修复 SDK 会话注册表的全部生命周期问题。客户端结束会话时应带认证和会话头发送 DELETE；应用的会话归属 TTL 与 SDK 内部会话清理不同，后者仍需后续单独处理。现有日志也没有建立心跳告警与数据库连接关闭之间的因果关系。

## 只读查询收尾保护

`ReadOnlyQueryScope.close()` 原先即使回滚失败也继续恢复自动提交，而且不对所有恢复失败显式安排连接淘汰。恢复自动提交可能提交尚未回滚的事务；并非所有驱动清理异常都带 Hikari 会识别的 08 类 SQLState。

修复后，回滚失败立即安排归还时淘汰并抛出原错误，不再恢复自动提交；自动提交或只读标记恢复失败也安排淘汰并保留原始异常。清理日志记录 requestId、ROLLBACK/RESTORE_STATE 阶段、是否成功标记淘汰和异常堆栈。已有查询/结果读取错误保持主异常，收尾与淘汰失败作为 suppressed 保留，不把数据库错误改成成功，也不重放 SQL。

4 项新增测试在原实现上失败，覆盖回滚失败、自动提交恢复失败、只读标记恢复失败及主异常保留；另增加真实 Hikari/H2 单槽池回归，确认物理连接失效后的清理释放池名额，下一次借用获得有效的新物理连接。这是对现场暴露的收尾路径的防护，不能证明现场连接最初关闭的诱因已经消除。

## 本地确认并修复的取消竞态

`RequestCancellation.dispatch()` 原先只在入队前检查注册项是否有效。取消线程繁忙时，语句/请求可能先结束并归还资源，已排队回调稍后仍会执行；已经开始的取消也没有与资源释放互斥。

新增 3 个确定性回归场景，修复前全部失败：语句注册关闭后的排队取消、整个请求关闭后的排队回调，以及取消执行期间提前释放注册项。修复后，回调真正执行时再次检查有效性，并让执行与注册项关闭互斥：未开始的过期取消跳过，已开始的取消退出后才允许 JDBC 资源继续关闭。

这证明了一个独立的本地生命周期缺陷，尚无现场证据证明它造成了反馈中的连接关闭。若驱动的取消调用卡住，资源关闭仍需等待驱动返回；本次未加入任意终止连接或写语句重放。

## 错误诊断与读取契约

- 现有 HTTP `X-Request-ID` 和审计字段继续保留；工具错误正文新增相同编号，连接/SQL/超时/内部错误记录带编号的原始异常堆栈，便于关联工具调用与连接审计。
- 超时文案现在说明数据库报告超时或中止、配置的语句时限及终止/回滚状态未确认，不再仅凭异常类型宣称本服务已发出数据库取消或测得 SQL 超过配置时间。错误码保持不变。
- `notifications/cancelled` 按 Agent、MCP 会话、JSON-RPC 请求 ID 定位；HTTP 读超时或断流本身不保证触发该通知，也没有同步查询最终状态查询接口。
- 源码分片参数按 UTF-16 单元计数。通用查询的文本上限也以 Java 文本长度计数，不是 UTF-8 字节；通用 `db_query` 没有每单元格完整长度字段，截断时不能依据行分页判定文本完整。直接查询时需用数据库 LENGTH/SUBSTR 获取并覆盖完整长度。
